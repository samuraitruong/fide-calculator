# Rating month migration operations

`supabase/migrations/002_rating_month.sql` and its `apps/web/supabase/migrations` copy are identical. Apply it to any database that does not yet have this schema before deploying clients that write `rating_month`. The configured project was inspected during this session and already contained the canonical column and the matching synchronization trigger; no additional database writes were performed by this session.

The transaction adds and backfills `rating_month`, validates a calendar-month constraint, sets NOT NULL, creates a profile/type/month index and synchronizes the legacy `month_key` through a trigger. Backfill uses valid existing `month_key` assignment before `game_date`. No rows are deleted and `game_date` is never updated. Existing `rating_month` values survive reruns; invalid existing explicit values abort validation rather than silently changing them. Backfill updates may advance the pre-existing `updated_at` trigger.

New clients can send canonical `rating_month` with or without `month_key`; legacy clients can send `YYYY-Mon` in `month_key`. If both assignments change, explicit `rating_month` wins. Date-only updates retain the assignment. The trigger always stores legacy `month_key` as English `YYYY-Mon` so older client filters continue to work. Invalid explicit canonical values and invalid legacy month updates are rejected.

Before production application, record the target project identifier and take a database backup. Validate against a disposable PostgreSQL instance initialized with migration 001. Seed games whose valid legacy and numeric keys differ from their dates, plus one invalid legacy key. Run 002 twice and verify row counts, game dates and assigned months. Test an old-client `month_key` move, a new-client `rating_month` move, a numeric `month_key` write, a date-only edit and rejection of `2026-13`/`2026-Jan` explicit values. Compare pre/post game date and rating values by ID. The migration requires a table lock and the index is created inside the transaction; schedule appropriately for database size.

Validation in this session: the shared helper tests and TypeScript build passed. Both migrations were executed against a disposable PostgreSQL engine (PGlite) initialized from migration 001 with an auth stub and legacy sample games. Backfill, repeat execution, unchanged game dates/ratings, old/new client writes, date-only edits, and invalid-month rejection passed. Read-only inspection of the configured Supabase project confirmed canonical non-null text rating_month values and the matching games synchronization trigger. Local stored records and imported records migrate automatically on load/write, preserving existing assignments and game dates; missing local IDs are assigned and persisted for stable edit/delete targeting.

If migration execution fails, the transaction rolls back. To roll back a deployed client, retain this additive schema and trigger: older clients remain compatible. A schema rollback after returning all clients to legacy behavior can drop `sync_game_rating_month`, `sync_game_rating_month()`, the new index, the constraint and the `rating_month` column, then `normalize_rating_month(text)`. That loses independent month assignments from the new column, so keep a backup and prefer the compatible additive schema. Do not roll back by resetting `game_date` or deleting games.
